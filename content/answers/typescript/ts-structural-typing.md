**При структурной проверке важен подходящий набор членов и их типов, а не совпадение названия объявления.** Объект с дополнительными полями может соответствовать более узкому контракту. Номинальная модель обычно связывает совместимость с именем или происхождением типа.

#### Как это работает

Совместимость позволяет передать более подробный объект туда, где требуется только name. Для свежего объектного литерала дополнительно проверяются лишние свойства: это помогает заметить опечатку, но не превращает тип в точную закрытую форму.

У `private` и `protected` классов также имеет значение происхождение членов. Поэтому структурную модель нельзя свести к безусловному сравнению любых одинаково написанных полей.

Статически узкое представление не скрывает поля от сериализации. Для отправки только разрешённых данных собирайте новый DTO из явного списка свойств.

#### Пример

```typescript
type Named = { name: string }
const user = { name: "Аня", age: 25 }
const named: Named = user // дополнительные данные не мешают
function greet(value: Named) {
  return value.name
}
greet(user) // "Аня"
// greet({ name: "Аня", age: 25 }) // Лишнее поле свежего литерала.
const dto = { name: user.name } // Реальная проекция данных.
```

#### Разбор примера

Named видит name, но присваивание user не удаляет age и не создаёт новый объект. Это позволяет передавать более подробные данные в функцию с узким контрактом. Если же цель - отправить наружу только разрешённые поля, нужно собрать новую запись; сужение статического представления само не является фильтрацией данных.
