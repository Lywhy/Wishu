Форма данных в JSON не обязана совпадать с моделью, удобной внутри приложения. Дата в DTO обычно приходит строкой, а доменный объект может требовать Date и дополнительные проверенные инварианты.

<!-- wishu:answer-block -->

#### Как это работает

Простое утверждение `as Domain` не создаёт экземпляры, не преобразует строки и не проверяет корректность дат. Сначала валидируйте транспортную структуру, затем выполните явное преобразование.

Для отправки данных обратно создавайте отдельную проекцию разрешённых полей. `Omit` и `Pick` меняют типовое описание, но не являются реализацией сериализации или удалением секретов. Разделение моделей также уменьшает случайную зависимость внутреннего кода от названий и nullable-полей конкретного API.

#### Пример

```typescript
type UserDto = { id: string; createdAt: string }
type User = { id: string; createdAt: Date }
function toUser(dto: UserDto): User {
  const createdAt = new Date(dto.createdAt)
  if (Number.isNaN(createdAt.getTime())) throw new TypeError("Некорректная дата")
  return { id: dto.id, createdAt }
}
// Перед toUser внешний JSON должен пройти проверку структуры DTO.
```

#### Разбор примера

ToUser создаёт Date из транспортной строки и проверяет получившийся timestamp, после чего возвращает новую доменную форму. Это преобразование действительно меняет данные. Оно предполагает уже проверенный DTO и не заменяет валидацию id и createdAt у произвольного JSON.

#### Типичная ошибка

> Аннотировать parsed JSON доменным типом и ожидать Date, методы класса или удаление полей.
