Контейнер, который только производит T, может допускать более конкретный T. Потребитель T должен принимать более широкий набор значений. Если контракт и принимает, и возвращает T, безопасная замена обычно требует большей осторожности.

#### Как это работает

При `strictFunctionTypes` функциональные свойства позволяют наглядно увидеть направления совместимости. TypeScript выводит поведение из структуры и содержит отдельные послабления, в частности для методов и изменяемых массивов; это не полностью строгая система доказательства.

Аннотации `in` и `out` в поддерживаемых объявлениях документируют и ограничивают ожидаемое направление при соответствующих сравнениях инстанциаций. Они не переписывают структурную семантику в произвольном сравнении и не исправляют неверную форму API. Начните с фактического использования T.

#### Пример

```typescript
type Producer<T> = { read: () => T }
type Consumer<T> = { write: (value: T) => void }
type Cell<T> = { read: () => T; write: (value: T) => void }
type Animal = { name: string }
type Dog = Animal & { bark(): void }
declare const dogs: Producer<Dog>
const animals: Producer<Animal> = dogs
```

#### Разбор примера

`Producer<Dog>` подходит потребителю `Producer<Animal>`, поскольку каждый возвращаемый Dog является Animal. Для write направление было бы обратным: принимающий только Dog не обязан справляться с любым Animal. Когда T участвует в обеих ролях, нужно проверять обе возможности замены.

#### Типичная ошибка

> Считать все `Box<T>` ковариантными или использовать in/out как приведение несовместимых структур.
