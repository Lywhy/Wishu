У стандартного `Promise<T>` типизируется успешное значение, но не исчерпывающий набор причин отклонения. `Result<T, E>` делает ожидаемый отказ частью возвращаемых данных и заставляет различить ветви по признаку результата.

<!-- wishu:answer-block -->

#### Как это работает

Это полезно, если отказ является нормальным бизнес-исходом, например неверный пароль или отсутствие записи. Неожиданные исключения по-прежнему могут выйти за пределы Result, если реализация их не переводит в соответствующий вариант.

Не стоит ловить всё и объявлять любую ошибку бизнес-отказом: так легко скрыть дефект программы. Сначала определите, какие исходы обязательны для обработки вызывающим кодом, и выберите единообразную границу преобразования.

#### Пример

```typescript
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E }
type FindError = "not-found" | "forbidden"

function label(result: Result<{ name: string }, FindError>): string {
  if (result.ok) return result.value.name
  return result.error === "not-found" ? "Не найдено" : "Нет доступа"
}
// Promise<Result<T, E>> описывает ожидаемые исходы,
// но сам по себе не запрещает неожиданное отклонение Promise.
```

#### Разбор примера

Проверка ok открывает value только в успешной ветви. В другой ветви label использует конечный набор предметных ошибок и выбирает понятную подпись. Если внутренняя реализация неожиданно выбросит исключение, сам тип Result его не перехватит и не превратит в error автоматически.

#### Типичная ошибка

> Считать Result доказательством, что функция больше никогда не выбросит исключение.
