**key сообщает React, какая запись списка соответствует прежней записи между рендерами.** Стабильный ключ помогает сохранить локальное состояние за нужными данными, даже когда порядок меняется.

<!-- wishu:answer-block -->

#### Как это работает

Используйте ID из данных, уникальный среди непосредственных соседей. Глобальная уникальность во всём приложении не требуется. Индекс опасен при вставке, удалении и сортировке: состояние поля может остаться в позиции, но относиться уже к другой записи. В действительно статичном списке без такой семантики риск иной, поэтому запрет индекса не является магией.

Случайный key на каждом рендере пересоздаёт элементы и теряет ввод. `useId` также не заменяет идентичность записи. Key ставят на элемент, непосредственно возвращаемый из map. Компонент не получает его как обычный prop: если нужен ID, передайте отдельный itemId. Для группы узлов используйте явный Fragment с key.

#### Пример

```jsx
items.map((item) => <EditableRow key={item.id} itemId={item.id} title={item.title} />)
// При сортировке EditableRow сохраняет состояние за item.id.
```

#### Разбор примера

После сортировки тот же item.id остаётся связан с той же EditableRow. Поэтому локальный ввод не переезжает к другой записи. Отдельный itemId нужен внутри компонента, поскольку key обслуживает сопоставление React и не передаётся обычным полем props.

#### Типичная ошибка

Поставить key на вложенный li внутри EditableRow, оставив элементы самого map без ключей.
