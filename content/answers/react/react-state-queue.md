**Каждый обработчик видит снимок state своего рендера.** Повторная запись count + 1 использует этот же снимок, а функциональные updater последовательно вычисляют значения из очереди.

<!-- wishu:answer-block -->

#### Как это работает

При count=0 три вызова setCount(count + 1) запрашивают значение 1. Три updater setCount(n => n + 1) дают 3. Можно смешивать замену и updater: setCount(5), затем setCount(n => n + 1) дают 6. Последующая замена снова перекроет накопленный результат.

Updater должен быть чистым. Не отправляйте в нём аналитику и запросы; в разработке React может повторно вызвать его для проверки. Batching уменьшает число промежуточных обновлений, но не меняет снимок в уже выполняющемся обработчике. Современная группировка распространяется и на многие async-callback, но не обещает единственный render для любого сценария. Setter не возвращает Promise ожидания commit.

#### Пример

```jsx
function increment() {
  setCount((n) => n + 1)
  setCount((n) => n + 1)
  setCount((n) => n + 1)
  // count здесь всё ещё из текущего рендера.
}
```

#### Разбор примера

Каждый updater получает результат предыдущего шага очереди, поэтому три прибавления дают 3. Чтение count внутри того же обработчика остаётся прежним. Это совместимые правила: очередь определяет будущий результат, а замыкание сохраняет текущий снимок.

#### Типичная ошибка

Использовать await setCount(...) как способ получить новое значение или помещать побочные эффекты в updater.
