**Тест конкурентного UI должен проверять видимые гарантии: актуальный результат, доступный ввод и правильное восстановление, а не универсальное число render.**

<!-- wishu:answer-block -->

#### Как это работает

React вправе повторить или прервать вычисления; dev-проверки добавляют свои вызовы. Управляйте завершением Promise и имитируйте смену входа, затем докажите, что старый результат не заменил новый. Не делайте реальный сетевой тайминг основой стабильности теста.

Отдельный performance-тест может измерять стоимость, но функциональный тест должен оставаться независимым от внутреннего расписания.

#### Пример

```jsx
await user.type(screen.getByRole("textbox"), "react")
// Подготовлены две управляемые попытки: старый запрос и запрос react.
await act(async () => {
  resolveLatestRequest()
})
expect(await screen.findByText("Результат react")).toBeVisible()
await act(async () => {
  resolveOlderRequest()
})
expect(screen.getByText("Результат react")).toBeVisible()
// Helpers завершают соответствующие Promise, act дожидается React-обновлений.
```

#### Разбор примера

Тест управляет разрешением запросов, позволяя более старому завершиться после нового. Итоговый экран должен сохранить последний пользовательский выбор. Количество повторных render при этом может меняться без нарушения функционального контракта.

#### Типичная ошибка

Требовать ровно один вызов функции компонента как доказательство корректности transition.
