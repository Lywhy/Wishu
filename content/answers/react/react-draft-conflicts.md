Подтверждённая запись и редактируемый черновик имеют разных владельцев и сроки жизни. Новые props не должны автоматически затирать несохранённый ввод без выбранной политики.

#### Как это работает

Определите базовую ревизию, признак изменений и действия при внешнем обновлении: сохранить draft, предложить перезагрузить или выполнить предметное слияние. При смене сущности key может осмысленно сбросить локальную форму, но при обновлении той же записи это может уничтожить работу.

После успешной отправки согласуйте draft с принятой версией. Ошибка сети должна оставить введённое значение. Проверка конфликтов параллельного редактирования окончательно решается серверным контрактом, а не одним React state.

#### Пример

```tsx
import { useState } from "react"
function TitleDraft({ initialTitle }) {
  const [draft, setDraft] = useState(initialTitle)
  return (
    <label>
      Название
      <input value={draft} onChange={(event) => setDraft(event.target.value)} />
    </label>
  )
}
// initialTitle - начальный снимок. Политика внешнего обновления задаётся отдельно.
```

#### Разбор примера

TitleDraft воспринимает initialTitle как начальную базу и затем хранит пользовательский ввод самостоятельно. Повторное получение props не стирает draft. Если продукт хочет принять новую серверную версию, это должен быть отдельный переход с понятной политикой сохранения или конфликта.

#### Типичная ошибка

> Копировать новые серверные props в state эффектом при каждом refetch и стирать пользовательский ввод.
