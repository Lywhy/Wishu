**При CSR браузер получает приложение и строит интерфейс после загрузки JavaScript.** SSR формирует HTML на сервере для запроса, а статический рендеринг - заранее, например при сборке. При необходимости интерактивности серверный HTML обычно гидратируется на клиенте.

#### Как это работает

Готовый HTML может улучшить первоначальное отображение и доступность содержимого для поиска, но результат зависит от задержек, объёма JavaScript и кеширования. SSR не делает весь код серверным: обработчики и клиентское состояние требуют выполнения в браузере.

#### Потоковый вариант SSR

Streaming позволяет отправить готовую оболочку, затем дополнять поддерживаемые области Suspense. Для Node используется `renderToPipeableStream`, для среды Web Streams - соответствующий readable API. После начала отправки нельзя произвольно поменять статус и заголовки: ошибки shell и поздних областей требуют разных решений. Прокси также может буферизовать чанки.

Это не делает любой fetch из клиентского эффекта серверным ресурсом. [Сценарий loading.tsx в Next.js](/questions/next-loading-streaming) применяет общую идею к маршрутам. [React: streaming API](https://react.dev/reference/react-dom/server/renderToPipeableStream).

#### Пример

```tsx
// Сервер: библиотека или фреймворк формирует React-HTML.
const html = renderToString(<App initialData={data} />)
// Клиент: data соответствует переданному сервером снимку.
hydrateRoot(container, <App initialData={data} />)
// Это схема двух сред, не единый запускаемый файл.
```

#### Разбор примера

Серверный вызов создаёт начальный HTML, а `hydrateRoot` подключает к нему клиентское дерево с теми же данными. Это два этапа одной схемы интерактивности. При статическом выпуске HTML первый этап происходит заранее; момент появления обработчиков всё равно определяется клиентской загрузкой.

#### Типичная ошибка

> Считать серверный HTML доказательством уже подключённых React-обработчиков. Интерактивность требует клиентской загрузки и гидратации.
