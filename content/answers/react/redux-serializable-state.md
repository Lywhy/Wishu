**Состояние и обычные действия Redux рекомендуют делать сериализуемыми.** Это облегчает воспроизведение, диагностику, сохранение и согласованные проверки.

<!-- wishu:answer-block -->

#### Как это работает

- Вместо экземпляра Date можно хранить согласованный ISO-текст или timestamp; вместо DOM-узла - идентификатор, если он нужен модели.
- Функция-thunk проходит через `middleware` и не является обычной записью в state. Исключение для обработанного `middleware` действия не означает разрешения хранить произвольные функции в store.
- `configureStore` включает проверки разработки с настраиваемыми исключениями. Их отключение не исправляет архитектурную проблему.
- Сериализуемость не означает безопасность или достоверность данных: runtime-валидация и права доступа остаются отдельными задачами.

#### Пример

```typescript
type InterviewState = {
  scheduledAt: string | null
  selectedId: string | null
}
// DOM-ref и незавершённый Promise не нужны в этом контракте.
```

#### Разбор примера

Строка scheduledAt хранит представление даты, которое можно записать, восстановить и увидеть в DevTools. Объект Date создают на границе отображения или вычисления. Аналогично в state обычно оставляют идентификатор ресурса, а не сам WebSocket, Promise или DOM-узел. Сериализуемость делает историю воспроизводимой, но не доказывает правильность схемы входных данных.

#### Типичная ошибка

> Выключить serializableCheck целиком ради одного случайного DOM-объекта.
