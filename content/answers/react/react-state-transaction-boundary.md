**Batching setter уменьшает промежуточные обновления UI, но не даёт бизнес-транзакции с атомарностью серверных операций и откатом.**

<!-- wishu:answer-block -->

### Механизм и границы

- Два владельца state могут иметь разные сроки жизни, ошибки и внешние подписки. Если переход должен быть логически неделимым, опишите его одним состоянием/reducer или специализированным store-контрактом.

- Побочные действия всё равно требуют отдельной согласованности. Если первый запрос завершился, а второй упал, группировка render не откатит первый.

- Тестируйте инвариант по состояниям системы, а не по одному визуальному commit.

### Пример

```jsx
dispatch({ type: "transferDraft", fromId, toId, amount })
// Один reducer проверяет допустимость всего локального перехода.
// Денежный перевод всё равно требует серверной транзакции.
```

### Типичная ошибка

Назвать несколько `setState` транзакцией и рассчитывать на автоматический откат внешних операций.
