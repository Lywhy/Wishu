**Service Worker - событийный посредник для контролируемых страниц и сетевых запросов в пределах scope.**

<!-- wishu:answer-block -->

### Как это работает

Он позволяет организовать офлайн-стратегию и кеширование через Cache API. Жизненный цикл включает установку и активацию; новая версия может ожидать, пока старые клиенты перестанут использовать предыдущую.

Он работает без DOM, обычно требует безопасный контекст и может останавливаться браузером между событиями. Поэтому постоянное состояние нельзя надёжно держать только в глобальных переменных.

WaitUntil продлевает обработку события, respondWith задаёт ответ на fetch. Регистрация не гарантирует немедленный контроль уже открытой страницы.

### Обновление и контроль страницы

Установленный новый worker может ожидать, пока старый обслуживает открытые страницы. Регистрация сама по себе не означает, что текущий документ уже контролируется новой версией. `skipWaiting` и `clients.claim` требуют продуманного обновления: смешение версий страницы и кеша может нарушить контракт. Cache API и HTTP cache - разные механизмы; стратегию обновления и офлайн-ошибки нужно задавать явно.

### Пример и его разбор

```javascript
async function registerWorker() {
  if (!("serviceWorker" in navigator)) return null
  return await navigator.serviceWorker.register("/sw.js", { scope: "/" })
}
// Код sw.js и политика кеширования определяются отдельно.
```

Register проверяет наличие API и регистрирует отдельный sw.js с нужным scope. Полученная регистрация ещё не гарантирует, что текущая страница немедленно обслуживается этой версией. Установка, активация и получение контроля являются разными событиями. Поэтому обновление офлайн-приложения нужно согласовать с живыми клиентами и версиями кешей, а не считать простой заменой скрипта.
