**Последний отправленный запрос не обязательно завершится последним.** Перед изменением интерфейса нужно проверить, относится ли ответ к актуальному запросу.

<!-- wishu:answer-block -->

### Практический подход

Каждому запуску присваивать возрастающий номер. Проверять актуальность перед применением и результата, и ошибки.

По возможности отменять прежний запрос через `AbortController`, чтобы не тратить ресурсы. Не считать debounce гарантией порядка: он уменьшает число запусков, но не исключает уже идущие запросы.

### Что проверить на практике

Пусть запрос A начинается первым, но завершается после B. На экране должен остаться результат B. Дополнительно проверьте очистку при уходе с экрана и ошибку отмены. Даже при `AbortController` защита актуальности полезна для операций, которые не поддерживают отмену или уже завершились до abort.

### Пример и его разбор

```javascript
function createLatestLoader(load, commit, onError) {
  let version = 0
  return async function search(query) {
    const current = ++version
    try {
      const data = await load(query)
      if (current === version) commit(data)
    } catch (error) {
      if (current === version) onError(error)
    }
  }
}
// load, commit и onError передаются приложением.
```

Каждый вызов search получает current, а общая version отражает последний запуск. Поздний результат старой операции не совпадёт с новой version и не попадёт в commit. Та же проверка защищает onError, чтобы устаревший отказ не испортил актуальный экран. Отмена может экономить ресурсы, но проверка актуальности определяет право менять интерфейс.

### Типичная ошибка

> Проверять актуальность успешного ответа, но показывать пользователю ошибку от устаревшего запроса.
