Повторяйте только подходящие временные сбои и операции с понятными гарантиями повторного выполнения. Ограничивайте попытки и время ожидания.

### Что уточнить

Операция идемпотентна или сервер поддерживает ключ идемпотентности? Тайм-аут клиента не доказывает, что сервер ничего не сделал. Является ли ошибка временной? Ошибка валидации и отсутствие прав обычно требуют исправления запроса, а не повтора.

Есть ли общий deadline и возможность отмены?

### Как снизить нагрузку

Используйте ограниченный exponential backoff с jitter, учитывайте Retry-After, если сервер его возвращает. Установите предел задержки и число попыток. Не добавляйте независимые повторы на каждом слое: их число перемножается.

### Что проверить

Успех с первой попытки; временная ошибка с восстановлением; исчерпание попыток; отмена во время ожидания; отсутствие повторной бизнес-операции при потерянном ответе.

### Пример и его разбор

```javascript
// Прикладной код должен передавать один ключ для повторов одной операции.
const operationId = crypto.randomUUID()
const createOrder = (signal) =>
  fetch("/orders", {
    method: "POST",
    headers: { "Idempotency-Key": operationId },
    body: JSON.stringify({ productId: 42 }),
    signal,
  })
// Сервер обязан реализовать идемпотентность: одного заголовка недостаточно.
```

OperationId создаётся один раз для одной логической операции и должен сохраняться при её повторах. Новый ключ означал бы для сервера другую операцию. Но сам заголовок ничего не гарантирует без серверной реализации хранения и проверки результата. Потеря ответа поэтому требует различать неизвестный исход, временный сетевой сбой и точно отклонённый бизнес-запрос.

### Типичная ошибка

> Повторять POST после тайм-аута с новым ключом и создавать дубли заказов.
