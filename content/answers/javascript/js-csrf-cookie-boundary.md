**Браузер может приложить подходящие cookie к запросу по правилам платформы. Злоумышленнику не всегда нужно прочитать ответ, чтобы нежелательная серверная операция была совершена.**

<!-- wishu:answer-block -->

### Как это работает

Серверная защита зависит от архитектуры: проверка Origin, подходящие CSRF-токены, SameSite и корректная семантика методов дополняют аутентификацию и авторизацию. Same-site и same-origin не совпадают, а CORS сам по себе не закрывает все способы отправить запрос.

Клиентский hidden-input без серверной проверки и скрытая кнопка не создают такой защиты. XSS имеет другую модель и может разрушить часть предпосылок CSRF-защиты.

### Пример и его разбор

```javascript
// Клиент может передать согласованный токен:
// fetch("/settings", { method: "POST", headers: { "X-CSRF-Token": token }, body })
// Его наличие имеет смысл только при правильной серверной проверке.
// Конкретную схему определяет серверная архитектура.
```

Заголовок X-CSRF-Token имеет значение только вместе с серверной проверкой его подлинности и связи с запросом. Наличие cookie подтверждает сессию, но не намерение пользователя выполнить конкретное действие. Поэтому аутентификация и защита от поддельного запроса решают разные задачи.

### Типичная ошибка

> Считать CORS или одно клиентское поле достаточной проверкой CSRF.
