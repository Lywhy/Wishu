**Для JSON-запроса обычно отдельно ожидают ответ `fetch` и чтение `response.json()`.** HTTP-статус 404/500 сам по себе не отклоняет `Promise` fetch: проверяйте `response.ok`.

<!-- wishu:answer-block -->

### Что обработать

1. Сетевую ошибку или отмену запроса.
2. Неуспешный HTTP-статус.
3. Ошибку чтения или разбора тела.
4. Несоответствие полученных данных ожидаемой структуре.

### Нюансы

Тело ответа - поток: повторное чтение обычно требует заранее созданной копии `response.clone()`. Отмена задаётся через `AbortSignal`; обработчики ошибки должны отличать ожидаемую отмену от реального сбоя.

Несколько поисковых запросов могут завершиться не по порядку: кроме отмены нужен контроль актуальности результата.

### Пример и его разбор

```javascript
async function fetchJson(url, signal) {
  const response = await fetch(url, { signal })
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`)
  }
  return await response.json()
}
```

Первая точка ожидания получает Response, а вторая читает и разбирает его тело. Между ними проверка ok превращает нежелательный HTTP-статус в явную ошибку нашего API. Успешный разбор JSON всё равно не доказывает ожидаемую структуру данных. Поэтому сеть, HTTP, формат и бизнес-контракт рассматривают как последовательные разные границы.

### Типичная ошибка

> Считать любой fulfilled fetch успешным бизнес-ответом и сразу использовать поля JSON без проверки.
