# Шаблоны доработок

Каждую задачу начинать с конкретного пользовательского результата, файла-владельца и соседнего рабочего примера. Не добавлять слои, store или общий компонент, пока в них нет необходимости. Команды и ручные сценарии проверки передавать пользователю.

## Новая страница

1. Найти ближайшую страницу в `src/pages/` и подходящий layout в `src/App.tsx`.
2. Уточнить URL и навигацию назад, хлебные крошки, источник данных, пустое состояние и ошибки.
3. Добавить страницу и минимально нужные компоненты. Брать существующие shadcn-компоненты; оформление через Tailwind. Общий стиль, цвета и анимации брать из соседнего каталога.
4. Зарегистрировать маршрут, при необходимости навигацию и правило footer. Добавить в карту проекта новую область, если она появилась.
5. Подготовить ручные сценарии: прямой URL, обновление, Back/Forward, узкий экран, клавиатура, светлая/тёмная тема, загрузка, ошибка и отсутствие данных. Пользователю предложить `pnpm check:ui`.

## Новый API-модуль

1. Посмотреть `server/src/modules/questions/` как пример структуры и `main.ts` как источник глобальных правил.
2. Описать вход, результат, ошибки, права доступа и повторную отправку. Добавить DTO, сервис, контроллер и модуль; зарегистрировать модуль в AppModule.
3. Для SQL использовать параметры и подходящую транзакцию. Если нужна структура БД, создать новую миграцию без правки применённых файлов. Работу со схемой выполнять по применимым правилам проекта.
4. Клиентский запрос и типы держать в `src/lib/`, состояние загрузки/ошибки - рядом с владельцем данных. Секреты остаются на сервере.
5. Обновить карту и документацию API. Пользователю предложить `pnpm check:server` и конкретные HTTP-сценарии; миграции и сервер запускает пользователь.

## Учебный материал

1. Выбрать раздел и учебную цель, проверить связи с вопросами и практикой.
2. В `src/data/learning-course.ts` подготовить последовательность лекция -> практика. Сначала механизм, затем пример, ограничение, самопроверка и ссылки на основы.
3. Markdown оформить через существующие учебные компоненты. Проверить смысл последовательности и источники, не исполняя примеры.
4. Практический блок связать с подходящей задачей; не создавать отдельный редактор и runner. Сохранить ID и правила отметки пройденного материала.
5. Пользователю предложить `pnpm check:ui` и сценарий прохождения, восстановления черновика и возврата к завершённому шагу.

## Практическая задача

1. Найти близкий PracticeTask и формализовать вход, выход, ограничения, допустимую мутацию и пограничные случаи.
2. Подготовить условие, пример, стартовый код, эталон и пояснение в подходящем файле `src/data/`. ID сохранить при уточнении существующей задачи.
3. Встроить проверку через существующий task-checker и sandbox. Не ослаблять изоляцию и не выполнять код решения на сервере агента.
4. Для обычной задачи готовить минимум 5 содержательных тестов: 2 базовых, 2 средних с рандомными входами, 1 сложный с рандомными входами. Сложность связать с требованиями. Для учебной практики действует отдельный договорённый формат одного теста под материал.
5. Учитывать входные данные, ожидаемое/фактическое значение, console.log, ошибки компиляции и тайм-аут. Отметка решения появляется только после принятия всех тестов.
6. Передать пользователю сценарии корректного, частичного и ошибочного решения; `pnpm check:ui` проверяет код приложения, но не заменяет запуск решений пользователем.

## Пакет вопросов

1. По индексу найти похожие учебные цели в нужном и соседних разделах.
2. Обновить coverageGoals выбранного подраздела. Уже раскрытый навык дополнить в каноническом вопросе.
3. Создать draft через content:new или импортировать список через content:import. Рассмотреть показанные кандидаты и пропущенные совпадения.
4. Заполнить ответ, примеры, нюансы, главную мысль, источники и связи. Уточнить learningGoal и keywords. После редакторского разбора перевести в ready.
5. Получить локальный отчёт и проверку, затем полный отчёт перед сборкой. Пользователь выполняет content:build, check:content и при необходимости db:seed.

Общие правила ответа: [question-authoring-policy.md](question-authoring-policy.md). Примеры команд: [development-workflow.md](development-workflow.md).
