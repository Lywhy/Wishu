# Подготовка и добавление вопросов

Редактируем исходники в `content/questions/<sectionId>/<subsectionId>.json`. Ответы хранятся отдельно в `content/answers`, поле answerFile ссылается на Markdown. Файл `server/database/seeds/questions.json` теперь является собранным артефактом для существующего PostgreSQL seed. Его не редактируем вручную.

## Файлы и ответственность

| Файл                                          | Назначение                                                        |
| --------------------------------------------- | ----------------------------------------------------------------- |
| `content/questions/catalog.json`              | Группы, разделы, подразделы, их ID, описания и порядок            |
| `content/questions/<раздел>/<подраздел>.json` | Границы темы, учебные цели, вопросы, ответы и редакторские данные |
| `content/generated/question-index.json`       | Компактный индекс без полных ответов и кода                       |
| `content/generated/question-coverage.json`    | Заявленные цели, связанные вопросы, уровни сложности и пробелы    |
| `content/templates/question.json`             | Образец структуры одного нового вопроса                           |
| `server/database/seeds/questions.json`        | Совместимый с сервером результат сборки, без editorial            |

Исходники и три собранных артефакта храним в Git. Зависимостей и отдельной базы для контентных инструментов нет. Скрипты на Node.js используют только стандартные модули, ничего не загружают из сети и не исполняют код примеров.

## Быстрый цикл

1. Найти близкие вопросы по индексу. Искать также в соседних разделах: без `--section` поиск идёт по всему каталогу.
2. Открыть один нужный файл подраздела. Уточнить цель в `coverageGoals` или добавить новую. Цель без опубликованных вопросов видна как planned.
3. Подготовить связанный пакет вопросов. Для того же навыка расширить существующий ответ с прежним ID. Отдельный прикладной вопрос связать с каноническим через relatedQuestionIds и понятные Markdown-ссылки.
4. Держать незавершённые ответы в draft. После редакторского разбора заполнить источники, выбрать ready и подтвердить scope цели через reviewed. Не переводить импортированные материалы в ready автоматически.
5. Получить отчёт до пересборки: он сравнивает исходники с текущим seed. Рассмотреть изменения, исключённые ID и кандидатов на повторы.
6. Собрать каталог и выполнить структурную проверку. Просмотреть изменения файлов. Затем отдельно применить seed.

```sh
pnpm content:find -- "замыкания"
pnpm content:find -- "receiver" --section javascript --limit 10
pnpm content:find -- "Promise" --section javascript --subsection asynchronous

pnpm content:report -- --section javascript
pnpm content:build
pnpm content:check
pnpm db:seed
```

Контентные команды разрешены агенту с 2026-11-07; приложение и seed запускает пользователь. `content:build` только формирует JSON; `content:check`, `content:find` и `content:report` не меняют файлы или базу. Поиск использует последний собранный индекс. Отчёт читает свежие исходники; после сборки опубликованные изменения уже станут его новой базой сравнения.

`db:seed` и `db:init`, в том числе из `server/`, сначала выполняют content:check. Если исходники изменились, нужна явная content:build. Установка/миграции, сборка сервера и запись в PostgreSQL происходят только по соответствующим командам пользователя. `db:migrate` не зависит от каталога.

## Учебная цель и редакторские данные

У файла подраздела есть scope - предметные границы темы - и coverageGoals. Каждая цель содержит id, title, description, requiredDifficulties и reviewed. Список требуемых уровней выбираем осмысленно; он может быть пустым, пока план не разобран. Не создаём базовый/средний/сложный дубль одного определения ради квоты.

У вопроса сохраняются прежние поля ответа. Добавляется editorial:

Для нового вопроса выбираем уникальный стабильный ID и следующий свободный order внутри подраздела. В шаблоне order: 0 - образец, его нужно заменить. Topic и moduleId берём у соседних вопросов того же раздела. SectionId/subsectionId задаются один раз на уровне файла.

| Поле               | Как заполняем                                                                    |
| ------------------ | -------------------------------------------------------------------------------- |
| learningGoal       | Что кандидат должен объяснить, применить или диагностировать                     |
| keywords           | Термины и синонимы для быстрого поиска, например closure и замыкание             |
| kind               | explanation, application или code-reading                                        |
| reviewStatus       | draft, imported или ready                                                        |
| goalIds            | Одна или несколько существующих целей из этого файла                             |
| relatedQuestionIds | Связанные канонические вопросы и закрепление, без самоссылок                     |
| sources            | Название и HTTP(S)-ссылка на документацию; для ready нужен хотя бы один источник |

Draft виден в индексе и отчёте, но исключён из seed и подсчёта опубликованного покрытия. Imported сохраняет уже доступный материал без заявления о редакторской проверке. Ready означает, что редактор подготовил вопрос к публикации, а не что программа доказала точность ответа. Опубликованный вопрос не может ссылаться на draft.

### История первоначального переноса

Перенесены все 719 вопросов в 103 файла подразделов. ID, тексты, сложность, порядок внутри подраздела и остальные поля сохранены. Контекст sectionId/subsectionId берётся из файла подраздела. Они не дублируются у каждого вопроса.

Начальная learningGoal скопирована из summary, keywords содержит понятия раздела и подраздела. Существующие HTTP(S)-источники и известные связи извлечены из Markdown. Это заготовка редакторского индекса, а не новый смысловой анализ всех ответов. У каждой темы создана общая core-цель с reviewed: false и без искусственно назначенных требований по сложности. При следующем расширении нужно разбить её на конкретные навыки и явно добавить незакрытые цели.

## Как читать карту покрытия

- planned: цель заявлена, опубликованных вопросов пока нет.
- needs-review: цель ещё не подтверждена редактором или среди связанных вопросов есть imported.
- partial: подтверждённая цель не имеет вопросов на некоторых требуемых уровнях.
- covered: подтверждённая цель имеет ready-вопросы и заявленные уровни.

Covered относится только к заявленной цели. Программа не узнает, что в плане забыли тему, не оценит качество объяснения и не гарантирует подготовку к любому собеседованию. Сам план периодически сопоставляем со спецификациями, документацией и практикой интервью.

## Что проверяется автоматически

Проверяются JSON, обязательные поля и типы, значения сложности/статусов, уникальные ID, порядок внутри подраздела, связи групп/разделов/подразделов, goalIds, известные внутренние ссылки на вопросы и HTTP(S)-форма источников. Наличие забытых файлов подразделов считается ошибкой. Для ready обязательны источники и дефис вместо длинного тире.

Проверка сравнивает seed, индекс и карту с исходниками. Пробелы, форматирование и порядок ключей объектов не влияют на результат; порядок элементов массивов значим. Валидация выполняется до записи сборки. Временный файл защищает каждый отдельный артефакт от обрыва во время записи; атомарной транзакции на все три файла нет, поэтому после прерванной сборки повторяем content:build.

VS Code получает JSON-подсказки через локальные схемы catalog.schema.json и question-bundle.schema.json. Команда content:check выполняет собственные проверки без стороннего schema-validator.

Поиск и кандидаты на повторы используют слова заголовка, цели и keywords. Учитываются совпадающие термины; автоматического понимания всех синонимов или embeddings нет. Процент в отчёте обозначает лексическое сходство, а не вероятность дублирования. Ответы с разными навыками не объединяются автоматически.

## Сохранность данных

Сборка не меняет PostgreSQL и не переносит прогресс. ID нельзя менять ради новой формулировки. Исключение вопроса из исходников или перевод в draft удаляет его только из собранного seed: upsert не удаляет уже существующую запись в базе. Для реального снятия с публикации, переименования ID или слияния записей нужен отдельный план работы с данными и прогрессом. Пользовательские вопросы из интерфейса остаются в PostgreSQL и автоматически в эти файлы не экспортируются.

Правила качества ответов: [question-authoring-policy.md](question-authoring-policy.md).

## Ускоренное создание и локальные режимы

Добавлены content:new, content:import и локальная content:check с --section/--subsection. В локальном режиме читаются только выбранные исходники, остальные связи берутся из последнего индекса; согласованность всех артефактов проверяет только полный запуск. Отчёт с фильтрами тоже читает исходники только выбранной области.

Ready-вопрос не должен содержать TODO-заготовки в заголовке, описании, ответе, выводе и учебной цели. Команды создания/импорта не переводят записи в ready и не меняют seed. [Полная инструкция и команды](development-workflow.md).

## Обновлённый контентный цикл

С 2026-11-07 контентные команды разрешены агенту. Ответы находятся в content/answers, подробные навыки - в coverageGoals, источники - в content/references/sources.json, решения - в content/decisions.json, планы - в content/batches. Отчёт по умолчанию сравнивает только изменения; --all включает полный обзор. [Актуальная инструкция](content-workflow-v2.md) уточняет прежние ограничения запуска и формат импорта. Приложение и seed запускает пользователь.

## Компактный контекст

По умолчанию вывод короткий, подробности включаются параметрами. Find/context используют компактный lookup; show открывает ответ по ID. Batch хранит рабочие ID и хеши, источники доступны через sourceRefs. [Текущий процесс](lean-content-workflow.md) уточняет параметры и заменяет прежние примеры подробного вывода по умолчанию.
