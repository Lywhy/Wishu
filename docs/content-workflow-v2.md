# Подготовка контента: полный рабочий цикл

## Что разрешено агенту

По разрешению пользователя от 2026-11-07 агент может самостоятельно выполнять контентные команды поиска, контекста, планирования, импорта, сборки и проверки. Это не разрешение запускать приложение, Docker, компилятор UI/сервера, lint проекта, миграции, PostgreSQL seed или решения задач. Пользователь запускает их самостоятельно. Контентные команды не используют сеть и не исполняют примеры.

## Контекст и план пакета

```sh
pnpm content:context -- --section javascript --subsection functions "замыкания"
pnpm content:context -- --section javascript --subsection functions --json
pnpm content:batch -- --new js-functions-review --section javascript --subsection functions
pnpm content:batch -- --id js-functions-review
```

Context собирает вопросы, учебные цели, соседние темы, пробелы заявленного плана, источники и редакторские решения. Полные ответы выводятся только с --answers; --limit ограничивает подборку вопросов, навыков и источников; --all выводит полную карту выбранной области. Соседние темы берутся из последнего индекса. Короткая сводка не заменяет чтения канонического ответа перед объединением.

Планы сохраняются в content/batches/<id>.json. ScopePass содержит цели, формулировки, кандидатов и оставшуюся работу первого прохода. AnswerPass - подготовку ответов, примеров и источников. Статусы и remaining обновляются в JSON по фактическому результату. Оба прохода агент выполняет самостоятельно; согласования каждого вопроса не требуется.

Baseline сохраняет ID и contentHash при создании плана. Поэтому отчёт с --batch сравнивает с началом пакета даже после content:build. Обычный отчёт сравнивает с последним собранным индексом. Старые ID в baseline - история, а не действующие ссылки. Для предварительного просмотра нового плана без записи добавьте --dry-run. План complete требует завершённых проходов без remaining.

## Markdown как исходник ответа

Вопрос хранит answerFile: answers/<section>/<id>.md относительно content/. Полный текст находится в content/answers; JSON содержит карточку, учебные цели и редакторские данные. Допускается прежний answer[], но ровно один из answer и answerFile.

Первый блок Markdown - короткий ответ. Последующие блоки отделяются строкой:

```html
<!-- wishu:answer-block -->
```

Пустая строка до и после разделителя обязательна. Он сохраняет прежний массив answer для UI. Это зарезервированный разделитель: для буквального показа такого комментария в примере используйте HTML-экранирование, а не точную строку разделителя. Обычный Markdown, списки, таблицы, сноски и fenced code внутри блока не требуют JSON-экранирования. Поле code остаётся отдельным примером/заданием, которое интерфейс может показывать до раскрытия ответа; примеры объяснения можно писать непосредственно в Markdown.

При первичном переносе существующие строки ответов сохраняются; дополнительные заголовки и новые объяснения автоматически не добавляются. Существующие ID и порядок не меняются. Сборка читает Markdown как данные, не исполняя код. AnswerFile ограничен каталогом content/answers, включая проверку символьных ссылок.

## Импорт готовых вопросов

```sh
pnpm content:import -- --file content/templates/full-import-example.json --section javascript --subsection functions --full
pnpm content:import -- --file content/templates/full-import-example.json --section javascript --subsection functions --full --write
```

Full импорт принимает JSON-массив объектов с title, summary, takeaway, learningGoal, одним из answer[], answerMarkdown или answerFile. Дополнительно поддерживаются id, difficulty, keywords, goalIds, code, pitfall, sources, relatedQuestionIds, kind, priority и popular. Sources содержит title и url. Markdown перед записью проверяется вместе с каталогом в памяти.

По умолчанию даже готовый материал сохраняется как draft. Для редакторски завершённого пакета можно явно указать --ready; тогда обязательны источники, заполненные поля и отсутствие TODO. Первый вызов без --write всегда предварительный. Совпадающие заголовки пропускаются; существующие ответы не перезаписываются. Обновление существующего канонического ответа выполняется в его исходнике с сохранением ID.

Для новых вопросов создаются отдельные .md. Файлы не перезаписываются. При ошибке обычной записи созданные текущим импортом Markdown удаляются, исходный JSON остаётся прежним; аварийное завершение процесса может оставить непривязанный Markdown или lock. Summary позволяет заметить редакторские недочёты, а JSON-каталог не начинает публиковать непривязанные файлы. Повторный импорт названий не создаёт копий.

## Карта навыков и приоритеты

CoverageGoals содержит обзорную core-цель и конкретные навыки, связанные с каноническими вопросами. При переносе подробное описание навыка сформировано из главного вывода существующего ответа, а не только из summary. RelatedSkillIds показывает связи для закрепления, не объявляя их автоматически обязательными prerequisite.

Reviewed остаётся false до смыслового пересмотра. Карта показывает, что уже представлено, но не доказывает полноту планирования. Новые нераскрытые навыки добавляем отдельными целями без вопроса: они видны как planned. Уровни сложности выбираем по требуемому рассуждению, а не по квоте.

Приоритет отличается от сложности:

- core: основные механизмы и прикладные случаи, с которых начинается подготовка.
- extended: дальнейшее углубление после основных целей.
- specialist: узкая специализация или необязательная для общего маршрута особенность.

При первичном переносе приоритеты назначены по тематике и конкретным узким API, а не по частотной статистике интервью. Их можно уточнять по целевой роли. Context начинает с core; сложный core-вопрос не становится второстепенным из-за сложности.

## Источники и редакторские решения

Content/references/sources.json хранит подборки для каждого подраздела: ссылки из существующих ответов и официальную документацию раздела как отправную точку. CheckedAt:null означает, что актуальная проверка страницы ещё не выполнена. Реестр не заменяет перепроверку версии и среды спорной возможности.

Content/decisions.json - журнал решений keep, expand, merge, separate, relocate и workflow. Для изменения записываем дату, область, затронутые действующие ID и причину. Реальное слияние ID по-прежнему требует отдельного переноса прогресса; запись в журнале ничего не меняет в базе.

## Отчёт и техническая сводка

```sh
pnpm content:report -- --section javascript --subsection functions
pnpm content:report -- --batch js-functions-review
pnpm content:report -- --section javascript --all
pnpm content:summary -- --section javascript --subsection functions
pnpm content:summary
```

По умолчанию кандидаты на повторы ищутся только для новых и изменённых записей против всего доступного индекса. --all возвращает полный обзор кандидатов выбранной области. Учитывается contentHash: изменения Markdown, редакторских данных и черновиков не теряются. При отсутствии изменений попарное смысловое сопоставление не запускается. Сходство остаётся лексической подсказкой, не основанием для автоматического объединения.

Summary возвращает JSON: добавления, изменения, исключённые ID, сложность и приоритеты, черновики, TODO, необходимость редакторского пересмотра и незакрытые цели. Ошибка структуры/связей возвращается как issues с ненулевым кодом выхода. Ссылки HTTP проверяются по форме URL, доступность страниц автоматически не проверяется.

## Завершение работы

```sh
pnpm content:report
pnpm content:summary
pnpm content:build
pnpm content:check
```

Эти команды теперь разрешены агенту. После сборки он сообщает изменения, состояние двух проходов и результаты проверки. Применение к PostgreSQL остаётся у пользователя: pnpm db:seed. Сборка по-прежнему выдаёт совместимые seed, индекс и карту покрытия, без редакторских полей в runtime-ответах.

## Компактный контекст

По умолчанию вывод короткий, подробности включаются параметрами. Find/context используют компактный lookup; show открывает ответ по ID. Batch хранит рабочие ID и хеши, источники доступны через sourceRefs. [Текущий процесс](lean-content-workflow.md) уточняет параметры и заменяет прежние примеры подробного вывода по умолчанию.
